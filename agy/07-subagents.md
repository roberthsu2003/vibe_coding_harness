# 08　Subagent 子代理

> ★★★ 深入　｜　[← 07 實戰情境](07-scenarios.md)　｜　[章節首頁](README.md)　｜　下一站：[09 權限設定與沙盒 →](09-permissions.md)

**這一站你會學到**：主代理與子代理的協同機制、如何檢視與呼叫子代理，以及如何使用全新的 **`/swarm`** 讓多個代理在共享留言板上平行協作與交叉審查。

---

## 1. 什麼是 Subagent（子代理）？

在大型專案開發中，如果讓單一 AI 代理包辦所有事，主對話很快就會充斥著大量搜尋過程、零碎日誌與無關的檔案內容，導致 Token 爆量且推理品質下滑。

**子代理（Subagent）** 是主代理在需要時派發出去的專屬助手：
- **獨立的 Context**：在獨立的工作階段中運行，只把最終結論或產出帶回給主代理。
- **特定工具與權限隔離**：例如指派一個「只讀」的探索代理，不允許修改檔案。
- **分工更明確**：研究、架構審查、圖片生成或特定領域規則撰寫各司其職。

---

## 2. 檢視可用代理

在終端機中，可以隨時透過 `agy agent` 查看當前環境註冊的所有代理：

```bash
agy agent
```

輸出範例（實際內容依環境與安裝的外掛而定）：

```text
Available agents:
research
image-generator
firestore-rules-author
```

在啟動 `agy` 時，也可以直接指定預設運作的代理角色：

```bash
agy --agent research
```

---

## 3. 常見的子代理角色

| 代理名稱 | 職責說明 | 權限特性 |
| :--- | :--- | :--- |
| **`research`** | 程式庫與專案研究。負責大範圍搜尋檔案、探索架構或整理技術文件 | 通常為唯讀環境，防止探索過程中意外改動代碼 |
| **`self`** | 繼承主代理設定的背景代理。適合在背景非同步執行長耗時子任務 | 具備完整工具鏈與相同模型設定 |
| **`image-generator`** | 針對 UI 設計需求生成或編輯圖形資產 | 專注圖形產出與路徑回傳 |
| **`firestore-rules-author`** | 專案安全規則（如 Firestore Security Rules）的專家代理 | 專門分析與強化安全規則防禦 |

---

## 4. 主代理如何調用子代理？

在與 `agy` 的對話中，你不需要手動編寫繁瑣的代理調度程式，主代理具備自主分工能力：

1. **直接指派任務**：
   ```text
   請派 research 代理去調查目前專案中所有使用到 deprecated API 的位置，並整理成清單。
   ```
2. **自動協同**：
   當你要求「深入研究一個新套件的整合方式並提供重構評估」時，主代理會自動調用 `invoke_subagent` 委派研究任務，研究完成後自動接手成果並在主視窗中呈現。

## 5. `/swarm`：平行代理協作團隊

當一個任務可以乾淨地拆分成多個**互不碰撞的檔案、套件或獨立問題**，或者你希望有另一個代理先幫你審查 Diff 並跑完測試時，可以使用 **`/swarm`**（目前為 Preview，支援 Google AI Pro 與 Ultra 方案）。

### 運作機制：協調者、工作代理與共享留言板

當你輸入 `/swarm <任務>` 時，目前的對話會變成團隊的**協調者（Coordinator）**，並自動組建團隊：

1. **拆分任務與指派專屬範圍**：協調者將工作拆成不會互相衝突的區塊（例如一個檔案或模組配一位代理），建立具名工作代理（如 `@parser`、`@api-tests`、`@docs`）或編號群組（如 `@fix-1`～`@fix-4`）。當多位代理需要同時修改或建置時，協調者可為每位代理配置獨立的 Git 工作副本（Workspace），避免改到同一個檔案。
2. **公開任務簡報（Public Brief）**：每位工作代理都在各自乾淨的對話上下文中啟動。協調者會在共享留言板（Shared Message Board）張貼公開簡報，明確定義每位代理負責的範圍、不可碰觸的邊界，以及「完成」的標準。
3. **專屬審查代理（`@verifier`）**：每 2～4 位工作代理通常會搭配一位 `@verifier`。它不直接改程式碼，而是專門閱讀 Diff、執行測試，並把發現的問題直接 `@` 回報給撰寫該區塊的代理修正。
4. **共享留言板與零消耗待命**：所有任務指派、代理間的提問、Diff 摘要與測試結果都公開張貼在同一個留言板上。閒置或等待回覆的代理會進入休眠（`Waiting`），**休眠期間完全不消耗 Token**，直到有人在留言板 `@mention` 它的名字才會自動喚醒。此外還有 `@monitor` 負責在全體靜默時喚醒卡住的環節。

> [!CAUTION]
> **注意額度消耗**：Swarm 中的每位成員都是獨立運作的 AI 代理，消耗模型額度（Quota）的速度會比單一對話快上許多。若某位成員額度用盡，它會自動暫停並顯示提示，不會無限重試；你可以請協調者幫該成員切換模型（保留原對話紀錄繼續執行）。

### 在 `agy` 終端機啟動與監控 Swarm

#### 1. 啟動 Swarm

在 `agy` 提示框輸入 `/swarm`（可按 `Tab` 補全）並描述目標與驗收方式：

```text
/swarm 為 src/utils/date.ts 與 src/utils/currency.ts 新增單元測試，並執行 npm test 確認全部通過
```

啟動後，對話框下方會出現 **Swarm 即時狀態列（Live Status Line）**，顯示 Swarm 標題、最新貼文與貼文數，以及正在執行的工作代理列表。任務完成後可按 **`Alt+X`** 關閉狀態列。

#### 2. 開啟全螢幕即時看板（Live Board）

輸入 **`/swarm board`** 或按下快捷鍵 **`Alt+S`**（macOS 終端機需設定將 Option 作為 Meta/Alt 鍵），即可開啟全螢幕即時看板，包含三個窗格：
- **Roster（成員名單）**：顯示每位成員的狀態（`working` 執行中、`waiting` 待命中、`killed` 已移除）、最後發言時間與使用的模型。
- **Posts（貼文動態）**：依時間排序的共享留言板貼文串。
- **Message（訊息內容）**：完整顯示目前選中貼文的排版內容。

**看板常用操作鍵：**

| 按鍵 | 功能說明 |
| :--- | :--- |
| `j` / `k` 或 `↓` / `↑` | 上下移動選取貼文、成員，或捲動訊息內容 |
| `g` / `G` | 跳到第一則或最後一則項目 |
| `Tab` / `Shift+Tab` | 在 Roster、Posts 與 Message 三個窗格之間切換 |
| `Enter` | 在 Posts 窗格顯示/隱藏訊息內容；在 Roster 窗格顯示/隱藏成員細節 |
| `Space` | 直接原地展開或收合選中的貼文 |
| `f` | 開關自動跟隨模式（Follow mode，自動停在最新貼文） |
| `p` | 篩選只看選中成員（或貼文作者）的發言；再按一次 `p` 或 `Esc` 清除篩選 |
| `z` | 將目前所在的窗格放大至全螢幕，或還原版面 |
| `o` | 直接開啟選中成員（或貼文作者）的獨立對話視窗 |
| `q` 或 `Esc` | 逐步返回或關閉看板回到提示框 |

### 引導團隊與審批工具權限

- **調整方向**：直接跟主對話的協調者（Coordinator）說要變更範圍或優先順序，協調者會在留言板上轉達給對應的工作代理。
- **私訊特定代理**：想直接回答某位工作代理的問題或追加指示，可在輸入框用 `@` 開頭點名（訊息只會送給該代理，不會貼到公開留言板）：
  ```text
  @verifier 請順便執行整合測試 npm run test:integration
  ```
- **快速處理權限請求**：
  - 按 **`Alt+J`**：立刻將焦點跳轉到下一個正在等待工具執行確認的子代理。
  - 按 **`Ctrl+K`**：不必離開主對話，直接快速批准狀態列提示中的子代理操作請求。
  - 輸入 **`/agents`**：查看所有 Swarm 工作代理清單並進入個別對話。

### `/swarm` 實戰 Prompt 範例

| 情境 | Prompt 範例 |
| :--- | :--- |
| **跨檔案平行開發** | `/swarm 為 src/routes/users.ts、src/routes/orders.ts 與 src/routes/products.ts 三個 API 加上輸入驗證，每個檔案分配一位 worker 並在旁新增測試，最後由 verifier 執行 npm test。` |
| **跨模型開發與交叉驗證** | `/swarm 為 pkg/httpclient 與 pkg/webhooks 加上指數退避重試機制。讓 verifier 使用與 worker 不同的模型來檢查競爭條件（race conditions），並執行 go test -race ./...。` |
| **平行調查效能或 Bug** | `/swarm 找出為什麼 CLI 啟動需要 4 秒。派三位唯讀 worker 分別調查模組匯入、設定檔載入與外掛探索，在留言板上交叉比對證據後，整理出依優先順序排列的修復清單。` |
| **多套件測試修復** | `/swarm 執行 pytest 找出所有失敗的測試，依套件分組，每個損壞的套件指派一位 worker 在不刪除 assertion 的前提下修好測試，最後由 verifier 重新跑完完整測試套件。` |

## 6. 多代理長期專案（`/teamwork`）

如果專案跨越多個階段與里程碑、需要先做需求訪談與規格確認，可輸入：

```text
/teamwork 把這個網站從 JavaScript 改寫成 TypeScript
```

這會先透過互動訪談釐清規格，再由專業分工角色依里程碑與審核關卡（Audit Gates）推進長期專案（僅限付費方案）。

---

## 7. 怎麼選？Subagents、`/boost`、`/swarm` 與 `/teamwork`

Antigravity 提供四種多代理機制，可依任務性質選擇：

| 比較項目 | Subagents（子代理） | `/boost` | `/swarm` | `/teamwork` |
| :--- | :--- | :--- | :--- | :--- |
| **最適合** | 委派單一分支任務（如查資料、跑測試） | 困難的 Bug、演算法或需要深度推理的重構 | 可拆分為獨立檔案、模組或問題的平行工作 | 全專案大規模遷移、長期模擬與跨階段專案 |
| **協作方式** | 子代理完成後直接回報給呼叫它的主代理 | 多層次架構探索不同假設並交叉驗證解法 | 具名工作代理與審查代理在共享留言板上協作 | 專業角色依里程碑計畫與審核關卡推進 |
| **啟動方式** | 主代理自動委派，或對話中點名指派 | `/boost <任務>` | `/swarm <任務>` | `/teamwork <目標>`（會先進行範圍訪談） |
| **典型耗時** | 數秒～數分鐘 | 數秒～數小時 | 數分鐘～數小時 | 數小時～數天 |
