# 06　多 Agent 協同：主管 AI 派工給小模型

> ★★★ 深入　｜　[← 05 底層原理](05-architecture.md)　｜　[章節首頁](README.md)　｜　下一站：[07 動手練習 →](practice/README.md)

**這一站你會學到**：為什麼要讓一個聰明的「主管 AI」指揮便宜的「小模型」，以及這件事在 Herdr 裡是怎麼運作的。

---

## 1. 為什麼要分工？

叫一個 AI 包辦全部（規劃、寫程式、測試、檢查），常見三個問題：

| 問題 | 說明 |
| :--- | :--- |
| 記憶塞爆 | 對話越來越長，AI 開始忘記前面的規則 |
| 顧此失彼 | 修好 A 功能，卻把 B 功能改壞 |
| 自己檢查自己 | 寫出有 bug 的程式，還說「測試全部通過」 |

解法和真實的開發團隊一樣：**分工**。

![Herdr 協同概念](assets/supervisor-subagent-concept.svg)

| 角色 | 比喻 | 做什麼 |
| :--- | :--- | :--- |
| 👑 **主管（Supervisor）** | 建築監工 | 拆解任務、訂驗收標準、派工、驗收。**自己不動手寫** |
| 🛠️ **小模型（SubAgent）** | 工班師傅 | 只專心做被交辦的一小件事 |
| 🏢 **Herdr** | 工地管理系統 | 給每個人獨立的工作區（窗格）、狀態燈號、對講機（CLI 指令） |

> 💡 **省錢又可靠**：聰明（較貴）的模型只負責動腦和檢查，大量的實作交給便宜或免費的小模型；而且由「另一個人」檢查，比較不會自圓其說。

## 2. 工作循環

![練習的工作循環](assets/practice-loop.svg)

1. 你用一句話說出需求。
2. 主管把需求整理成**任務卡**，訂好**驗收標準**，先給你確認。
3. 小模型在自己的窗格裡動手做。
4. 主管**親自驗收**（跑測試或檢查程式）。不合格就把錯誤訊息交給小模型修改，最多 3 次。
5. 合格後回報給你。

---

## 3. 在 Herdr 裡怎麼運作？

![Supervisor 與 SubAgent 底層架構](assets/supervisor-subagent-arch.svg)

主管 AI 不需要知道小模型是哪一家的 AI。它透過 Herdr 的 CLI 指令，**像真人一樣打字給小模型，再讀回畫面**（原理見 [05 底層原理](05-architecture.md#3-pty給程式戴上vr-眼鏡)）：

| 主管想做的事 | 使用的指令 |
| :--- | :--- |
| 開一個窗格給小模型 | `herdr pane split --current --direction right --no-focus` |
| 在窗格裡啟動小模型 | `herdr agent start coder --kind opencode --pane <窗格ID>` |
| 派工並等它做完 | `herdr agent prompt coder "任務內容" --wait` |
| 查看狀態 | `herdr agent get coder` |
| 讀它的回覆 | `herdr agent read coder` |
| 收工 | `herdr pane close <窗格ID>` |

> 完整的指令說明與範例請看 [CLI 指令與疑難排解](cli.md)。

## 4. 怎麼讓主管 AI 知道要這樣做？

把「主管工作手冊」放在專案資料夾，讓主管 AI 啟動時自動讀取。本教材使用 agy（Antigravity CLI）當主管，手冊檔名是 **`GEMINI.md`**：

👉 [GEMINI.md 主管工作手冊](practice/GEMINI.md)

手冊裡規定了：

- 先產生任務卡給使用者確認，再開始動手。
- 自己訂驗收標準（測試、檢查程式），放在小模型看不到的資料夾。
- 派工時告訴小模型「你是 SubAgent，不要執行 herdr 指令」。
- 驗收不合格就退回修改，最多 3 次。
- 需要時用 git worktree 隔離，審查後才合併。

> [!WARNING]
> **手冊不要取名為 `AGENTS.md`。** 小模型 OpenCode 會自動讀取 `AGENTS.md`，讀到主管規則後會誤以為自己是主管，跑去查詢自己的狀態而卡住。agy 會自動讀 `GEMINI.md`，OpenCode 不會，兩邊才不會搞混。

---

## 5. 最佳實踐

| 原則 | 說明 |
| :--- | :--- |
| **一個任務一個 worktree** | 多個小模型同時改程式時，各自在獨立的 git worktree 工作，就不會互相覆蓋檔案 |
| **任務切小** | 「補一個測試」「改一個函式」比「做完整個網站」成功率高很多 |
| **驗收要客觀** | 用測試或檢查程式判斷，不聽小模型自己說「完成了」 |
| **視窗要夠大** | 窗格太窄時，小模型可能收不到任務，請把終端機視窗最大化 |
| **人隨時可以接手** | 點一下小模型的窗格，就能直接看它在做什麼、親自操作 |
