# 第 2 關：不合格就退回

> 🎯 第 2 關／共 6 關　｜　[← 第 1 關](../01-first-subagent/README.md)　｜　[關卡地圖](../README.md)　｜　[第 3 關 →](../03-test-loop/README.md)　｜　⏱ 約 5 分鐘

## 學習目標

- 看到完整的**「檢查 → 不合格 → 退回修改 → 再檢查」**循環。
- 理解**驗收標準**的用途：讓「合不合格」有客觀的依據，而不是憑感覺。
- 學會用一般的話告訴主管「要怎麼派工」。

![退回修改的過程](../../assets/lesson-retry-rounds.svg)

---

## 對 agy 說

```text
請小模型寫一份 Yazi 的介紹給初學者看。第一次只告訴它主題就好，你另外訂嚴格的標準檢查，不合格就把問題告訴它，叫它改到通過。
```

> 💡 為什麼要說「第一次只告訴它主題」？
> 如果 agy 一開始就把所有要求都告訴小模型，小模型常常一次就過關，你就看不到退回修改的過程。這句話是為了練習而刻意安排的。

## 你會看到什麼

### 1. 任務卡

這次的驗收標準是一支**檢查程式**（`checks/yazi-intro/check_doc.py`），內容類似：

```text
## 驗收標準
  • 檢查指令：python3 checks/yazi-intro/check_doc.py
  • 字數 500 字以上
  • 必須有這些段落標題：簡介、安裝、常用快捷鍵、給初學者的建議
  • 必須提到：Rust、終端機、檔案預覽
```

確認後回覆「好，開始」。

### 2. 退回循環（大約 2～5 分鐘）

小模型寫完第一版，agy 執行檢查程式，通常會看到：

```text
❌ 驗收不通過，共 2 個問題：
  1. 缺少標題「## 三個常用快捷鍵」
  2. 缺少標題「## 適合誰使用」
```

agy 把這段**錯誤訊息原文**交給小模型，小模型修改後再檢查一次，直到出現：

```text
✅ 驗收通過
```

### 3. 回報

agy 會整理每一輪的結果，例如：

```text
• 總共跑了 3 輪
  - 第 1 輪：缺少兩個段落標題
  - 第 2 輪：快捷鍵用了數字清單，檢查程式只認 - 清單或表格
  - 第 3 輪：通過
```

> 如果第 1 輪就通過了也沒關係，代表小模型這次猜得很準。可以做變化題，或換一個主題再試一次。

## 想一想

1. 打開 `checks/yazi-intro/check_doc.py`，它檢查了哪些項目？哪一項最容易讓小模型失敗？
2. 為什麼 agy 要把「錯誤訊息原文」交給小模型，而不是自己改？
3. 驗收標準太鬆或太嚴，各會發生什麼事？

## 變化題（換句話再做 2～3 次）

- 「請小模型寫一份 Git 的入門介紹。第一次只說主題，你訂標準檢查：一定要有『安裝』和『第一次 commit』兩段，不合格就叫它改。」
- 「請小模型寫一篇 200 字以內的自我介紹範本，你檢查字數不能超過 200 字，而且要有『興趣』這個段落。」
- 先讓 agy 正常派工（**不要**說「只告訴它主題」），比較看看：小模型是不是一次就通過了？

## 🔧 進階：自己下指令（選修）

agy 在背後重複做這三件事：

```bash
python3 checks/yazi-intro/check_doc.py                    # 1. 執行檢查，取得錯誤訊息
herdr agent prompt writer "驗收不通過：<錯誤訊息>，請修改" \
  --wait --timeout 300000                                 # 2. 把錯誤交給小模型，等它改完
python3 checks/yazi-intro/check_doc.py                    # 3. 再檢查一次
```

自己動手試試：打開 `checks/yazi-intro/check_doc.py`，把字數要求調高，再請 agy「用同一份檢查程式重新驗收一次」，看看會發生什麼事。
